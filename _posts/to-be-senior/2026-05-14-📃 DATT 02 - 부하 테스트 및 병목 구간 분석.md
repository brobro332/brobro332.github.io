# 프로젝트 개요

DATT는 위치 기반 장소 기록 및 공유 플랫폼이다.

현재 검색 구조는 사용자 요청 시마다 실시간 크롤링을 수행한다.

```text
Client
    ↓
Spring Boot
    ↓
FastAPI Crawling Engine
    ↓
External Place Sources
    ↓
PostgreSQL(PostGIS)
```

Week1-Day1에서는:

- API 응답 시간 로깅
    
- 크롤링 시간 로깅
    
- DB Query 시간 로깅
    

등 계측 환경을 구축했다.

이번 작업에서는 실제 부하 테스트를 통해:

> "어디가 얼마나 느린가?"

를 수치 기반으로 분석하는 것을 목표로 한다.

# 현재 문제 상황

현재 구조에서는 사용자 요청마다:

- FastAPI 호출
    
- 외부 사이트 접근
    
- 데이터 가공
    
- DB 저장
    

이 모두 수행된다.

```text
사용자 요청
    ↓
Spring API
    ↓
FastAPI 크롤링
    ↓
외부 사이트 접근
    ↓
데이터 가공
    ↓
DB 저장
    ↓
응답 반환
```

즉:

- 외부 네트워크 상태
    
- 크롤링 처리 시간
    
- 저장 처리 시간
    

이 모두 응답 시간에 직접 영향을 주는 구조다.

---

# 문제 현상

```text
- 검색 응답 시간이 매우 불규칙함
- 특정 지역 검색 시 수 초 이상 지연 발생
- 동시 요청 증가 시 응답 시간이 급격히 증가
- 카테고리 변경 시 반복적인 재크롤링 발생
```

---

# 발생 조건

- 광범위한 지역 검색
    
- 데이터 개수가 많은 경우
    
- 동시 요청 증가
    
- 외부 사이트 응답 지연
    

테스트 대상 지역:

- 인천
    
- 강남
    
- 홍대
    
- 성수

# 코드 변경 사항

# Before

기존에는 별도 부하 테스트 환경이 존재하지 않았다.

```java
@GetMapping("/search")
public ResponseEntity<?> search(String keyword) {

    return ResponseEntity.ok(
            placeService.search(keyword)
    );
}
```

---

# After

k6 기반 부하 테스트 환경 추가.

```javascript
import http from 'k6/http';
import { sleep } from 'k6';

export default function () {

    http.get(
        'https://datt-prd.xyz/api/search?keyword=인천'
    );

    sleep(1);
}
```

---

# Trade-off

이번 작업으로 인해 발생하는 Trade-off:

|장점|단점|
|---|---|
|실제 병목 위치 확인 가능|테스트 환경 구축 비용 증가|
|개선 전 기준 데이터 확보 가능|로그 및 측정 데이터 관리 필요|
|P95/P99 기반 분석 가능|부하 테스트 환경 유지 필요|

---

# 운영 관점에서의 고려 사항

운영 환경에서는 단순 평균 응답 시간보다:

- P95
    
- P99
    
- Error Rate
    

가 더 중요하다.

특히 외부 I/O 기반 구조에서는:

- Timeout
    
- Retry
    
- Circuit Breaker
    

전략이 필수적이다.

또한:

- 외부 API 장애
    
- 크롤링 실패
    
- 네트워크 지연
    

이 전체 서비스 장애로 전파될 가능성이 존재한다.
