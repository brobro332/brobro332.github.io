# DATT 성능 병목 분석 및 개선 전략 수립

# 프로젝트 개요

DATT는 위치 기반 장소 기록 및 공유 플랫폼이다.

현재 구조는 다음과 같다.

```text
Client
    ↓
Spring Boot
    ↓
FastAPI Crawling Engine
    ↓
External Place Sources
    ↓
PostgreSQL(PostGIS)
```

초기 구조에서는 사용자 검색 요청 시마다 실시간 크롤링을 수행하도록 설계했다.

하지만 프로젝트를 운영하면서 다음과 같은 문제를 발견했다.

---

# 현재 문제점

## 1. 검색 응답 속도 지연

특히 다음과 같은 상황에서 응답 속도가 급격히 느려졌다.

- 지역 범위가 넓은 경우
    
- 카테고리 검색이 많은 경우
    
- 외부 사이트 응답이 느린 경우
    

예시:

- 인천
    
- 강남
    
- 홍대
    

등 광범위한 지역 검색 시 체감 성능 저하가 심했다.

---

## 2. 카테고리 전환 지연

카테고리 변경 시마다:

- 재크롤링
    
- 데이터 가공
    
- DB 저장
    

과정이 반복적으로 발생했다.

결과적으로 사용자 경험(UI/UX)이 저하되었다.

---

## 3. 구조적 문제

현재 구조는 사실상 아래와 같은 형태였다.

```text
사용자 요청
    ↓
Spring API
    ↓
실시간 FastAPI 크롤링
    ↓
외부 사이트 접근
    ↓
DB 저장
    ↓
응답 반환
```

즉:

- 외부 I/O
    
- 네트워크 지연
    
- 크롤링 처리 시간
    

이 모두 사용자 응답 시간에 직접 영향을 주는 구조였다.

# 측정 전략

## 1. Spring API 응답 시간 로깅

Interceptor 또는 Filter를 활용하여 API 응답 시간을 기록한다.

예시:

```text
[SEARCH_API]
keyword=인천
category=cafe
durationMs=8420
status=200
```

---

## 2. FastAPI 크롤링 시간 측정

크롤링 시작/종료 시간을 기록한다.

예시:

```text
[CRAWLING]
keyword=인천
category=cafe
durationMs=6210
resultCount=42
```

---

## 3. DB 처리 시간 측정

Query 및 Insert 시간을 별도로 측정한다.

예시:

```text
[DB_QUERY]
query=searchPlaces
durationMs=180
```

```text

    ↓

    ↓

    ↓
응답
```
